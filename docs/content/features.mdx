# Features

## Public repository analysis (zero authentication required)

Analyze any public GitHub repository directly by owner and name or full repository URL.
Provides instant visibility into community velocity, star growth history, and release timelines
without requiring visitors to sign in with GitHub OAuth.

## Star history & velocity

Interactive trajectory of repository stargazers with derived velocity metrics:

- 7-day and 30-day star growth
- Current weekly velocity (stars per week)
- Milestone achievements

## Release event correlation

Major releases fetched from GitHub and plotted against the repository timeline. Provides
contextual awareness of growth around key launches using clean publication dates.

## Traffic dashboard & 14-day limit bypass

Per-repository views, clones, top referrers, and popular pages over the last
14 days, with charts powered by Recharts. Private traffic analytics are unlocked
for authenticated owners and collaborators.

## Deterministic metrics & contextual AI insights

Deterministic analytics calculate star velocity, period comparisons, and release highlights in pure TypeScript.
The AI insights panel separately receives the repository's aggregated traffic telemetry and calls the Anthropic
Messages API (`claude-haiku-4-5`) to stream a concise, actionable summary of views, unique visitors, top referrers,
and popular content paths. Requires `ANTHROPIC_API_KEY`; degrades gracefully (HTTP 503) when not configured.

## Daily snapshots (beyond GitHub's 14-day window)

GitHub only serves the last 14 days of traffic. A Cloudflare **Cron Worker**
runs daily, reads the repos you've opted in to track, fetches their traffic, and
upserts one row per day/metric into a **D1** database. The dashboard's
"Historical traffic" panel then renders the full accumulated timeline.

- **Opt in:** the "Track this repo" button stores your repo + token in D1.
- **Read history:** `GET /api/snapshots?owner=…&repo=…` returns merged daily history.

## Growth signals

The repository overview checks complete UTC days for views and clones. It compares
the latest completed day with the median of at least five observations from the
preceding seven days. A spike needs at least twice the baseline and ten extra
events; a drop needs a baseline of at least 20, half the usual count or less,
and ten fewer events. Seven-day totals are compared only when both weeks have
all seven days. Public star signals compare two complete seven-day windows.

The pure analytics engine also supports referral-share changes, new leading
referrers, and popular-path surges when comparable historical windows are
available. GitHub's current top-referrer and path responses alone do not supply
those older windows, so the web overview does not invent them. A nearby release
is shown as timing context, never a claim that it caused the change.

## Export your archive

On the historical traffic panel, use **Export CSV** or **Export JSON** to download
the D1 snapshots collected for a repository. Exports contain raw daily metric
rows (`day`, `metric`, `count`, `uniques`) in ascending date order. They can be
empty before tracking begins. The export route checks both your signed-in
session and current GitHub traffic access, and restricts the D1 query to your
own snapshot records. Use optional `from` and `to` ISO dates to narrow a large
archive. The response is private and never cached publicly.

## Weekly report preview

Authorized maintainers can preview the latest seven complete UTC days from the
repository's Insights tab. The report combines D1 views, unique views, clones,
unique clones, available public star growth, releases during the period, and
deterministic growth signals. Traffic totals are shown only when all seven days
were captured; partial data is labeled unavailable rather than zero. Public
star metrics can be unavailable for private repositories or incomplete star
history. Previewing alone does not send email; delivery needs a separate opt-in.

## Weekly email

When delivery is configured by the deployment owner, authorized maintainers
can opt in from the Insights tab. The recipient is their verified primary
GitHub email; the app never accepts an arbitrary address. The hourly Cron
Worker sends the report on Monday morning in the selected IANA timezone, with
up to two retry hours. A delivery ledger and provider idempotency key prevent
duplicate emails. Owners can turn email off from the same tab. The report uses
completed UTC days and labels missing traffic or star data unavailable. It also
uses stored GitHub top-referrer and popular-path captures when available.
The Worker rechecks GitHub traffic access before delivery and removes the email
subscription if that access has been revoked.
Those source lists each cover GitHub's rolling 14-day window; comparing two
captures about a week apart describes a share change, not a precise weekly
referral count or proof that an external post caused growth.

## Traffic badge (the viral loop)

Every tracked repo gets a public, embeddable SVG badge of its **total accumulated
views** — the number GitHub discards after 14 days. Drop it into any README and it
links back to your deployment:

```md
[![Repo traffic](https://github-traffic-analytics.ali-ammari.workers.dev/api/badge?owner=you&repo=your-repo)](https://github-traffic-analytics.ali-ammari.workers.dev)
```

**Endpoint:** `GET /api/badge?owner=<o>&repo=<r>`

- Returns `image/svg+xml` (a Shields-style pill, dark label + electric-cyan value).
- **Public & unauthenticated** — it exposes only a single aggregate view count for a
  repo whose owner opted into tracking; no per-user or private data is revealed.
- **Never 404s:** returns a graceful `no data` / `error` badge so the image always
  renders, even before the repo has snapshots or off the Cloudflare deployment.
- Cached at the edge for one hour (snapshots change at most once a day).
